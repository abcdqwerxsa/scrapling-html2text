## 前言

在我的内网物理机 Kubernetes 环境中，需要一种方式让外部可以访问集群内的应用。同时，我对这套方案有几个明确的要求：

  1. 1\. **高可用**
  2. 2\. **访问地址固定**
  3. 3\. **可以统一限制访问来源**

其中第三点尤其重要——我不希望在每台服务器上单独配置防火墙规则，这样不仅维护成本高，而且容易出错。我更倾向于通过配置文件来实现，也就是一种 **声明式(Declarative)** 的访问控制方式。

在 Kubernetes 中，对外提供服务通常是通过 Service 来实现的。围绕这一点，我整理了几种常见的对外访问方式，做一个对比：

这个表有点长，也可能有纰漏，欢迎大家留言讨论

综合来看，我最终选择了：

> Service + LoadBalancer

但问题来了——

在物理机环境下，并没有云厂商提供的 `LoadBalancer`。

这时候，就需要 **MetalLB** 登场了。

## MetalLB 的介绍

MetalLB 是一个专门为 Kubernetes 裸机（物理机）环境设计的组件，用来解决一个核心问题：

> 让 `Service type=LoadBalancer` 在没有云厂商的情况下也能用

用一句话理解它

> MetalLB = “把云厂商的负载均衡能力，搬到你自己的机房里”

GitHub: https://github.com/metallb/metallb  
官网: https://metallb.universe.tf/installation

## 安装

MetalLB 官方提供多种安装方式：

  * • YAML
  * • Helm
  * • Operator

由于我的环境是**离线环境** ，这里选择使用 **YAML 方式安装** 。

这种方式非常直接，我很喜欢，一个 YAML 文件即可完成部署，适合当前这种轻量场景。

当然，对于后续像 CNPG、VictoriaMetrics、Rook-Ceph 这类复杂组件，还是需要 Helm / Operator 来管理，要仔细研究清楚，花费的时间比较长。

### 1\. 调整 kube-proxy（关键步骤）

如果 `kube-proxy` 使用的是 **IPVS 模式** ，需要开启 `strictARP`，否则 MetalLB 无法正常工作。
```

kubectl edit configmap -n kube-system kube-proxy
```

修改配置
```

apiVersion: kubeproxy.config.k8s.io/v1alpha1  
kind: KubeProxyConfiguration  
mode: "ipvs"  
ipvs:  
  strictARP: true # 修改这里
```

重启 kube-proxy
```

kubectl -n kube-system rollout restart daemonset kube-proxy
```

### 4\. 工作模式选择

MetalLB 支持两种工作模式

  * • Layer2（L2）模式
  * • BGP 模式

#### 1\. Layer2 模式

✅ 优点

  * • 部署简单：无需改动网络设备，开箱即用
  * • 兼容性好：适用于绝大多数内网/物理机场景
  * • 无额外依赖：不需要 BGP 或路由器支持
  * • 易于排障：基于 ARP，问题路径清晰、定位直观  
❌ 缺点
  * • 单节点瓶颈：同一时间只有一个节点承载流量
  * • 扩展性有限：无法横向分担入口流量
  * • 故障切换较慢：依赖 ARP 更新，通常为秒级
  * • 带宽受限：受限于单节点网卡能力

简单来说：

> Layer2 = 能用、好用，但不适合高流量场景

它的核心限制主要集中在两点：

  * • **单节点承载（天然瓶颈）**
  * • **故障切换依赖 ARP（不够快）**

####  2\. BGP 模式

✅ 优点

  * • 无单点瓶颈：多个节点可同时对外提供服务（ECMP）
  * • 性能更优：流量走最优路径，减少中间跳转
  * • 故障切换快：依赖路由收敛，切换速度更快
  * • 扩展性强：适合大规模、高并发场景  
❌ 缺点
  * • 依赖网络设备：需要支持 BGP 的交换机或路由器
  * • 配置复杂：涉及 ASN、邻居、路由策略等
  * • 排障困难：问题可能出现在网络层，而不只是 K8s
  * • 运维门槛高：需要一定网络经验

一句话总结：

> BGP = 更强、更快，但更复杂

#### 3\. 选型结论

  * • BGP：适合有网络基础设施、追求性能和扩展性的生产环境
  * • Layer2：适合内网、物理机、小规模或对性能要求不高的场景

由于我的环境：

  * • 没有 BGP 路由器支持
  * • 更关注简单可控、快速落地

所以最终选择：

> Layer2 模式

不过，我还是不禁有些好奇，BGP 模式一般是在哪些地方使用，存在即合理，肯定有其使用场景，但是 MetalLB 是在物理机环境安装的（或者是无法接触云 LB 的地方），可能是在 IDC 内部或者内网，内网中配置 BGP，这到底是什么业务量，我难以想象。

## Layer 2 模式配置

### 创建 IPAdressPool

MetalLB 通过 IP 地址池来分配对外的 VIP，可以：

  * • 定义多个地址池
  * • 支持 CIDR 范围
  * • 同时支持 IPv4 / IPv6

worker-ip-pool.yaml
```

apiVersion: metallb.io/v1beta1  
kind: IPAddressPool  
metadata:  
  name: worker-ip-pool  
  namespace: metallb-system  
spec:  
  addresses:  
    - 192.168.2.121/32
```

应用配置
```

kubectl apply -f worker-ip-pool.yaml
```

结果
```

[<REDACTED>@k8s-octarine-01 metallb]$ kubectl apply -f worker-ip-pool.yaml  
ipaddresspool.metallb.io/worker-ip-pool created
```

### 创建 L2Advertisement（关键）

L2 模式的本质是：

> 通过 ARP 响应，把 VIP “声明”为某个节点的地址

也就是说：

  * • VIP 并不会真正绑定到网卡
  * • 而是由某个节点“对外宣告”自己拥有这个 IP

`L2Advertisement` 的作用就是控制：

> 哪些节点可以对外宣告这些 IP（谁来接流量）

l2adv-range-worker-ip.yaml
```

apiVersion: metallb.io/v1beta1  
kind: L2Advertisement  
metadata:  
  name: l2adv-range-worker-ip  
  namespace: metallb-system  
spec:  
  ipAddressPools:  
    - worker-ip-pool  
  nodeSelectors:  
    - matchLabels:  
        node-role.kubernetes.io/worker: "true"
```

这里做了两件事：

  1. 1\. 只使用 `worker-ip-pool` 这个地址池
  2. 2\. 只允许带有 `worker` 标签的节点对外宣告 VIP  
应用配置

```

kubectl apply -f l2adv-range-worker-ip.yaml
```

## 一些问题？

刚开始部署 MetalLB 的时候，我还是个纯萌新，踩了不少坑，也有很多疑问。这里整理几个当时最困惑、也是最常见的问题。

### Q1：我只需要指定 `type: LoadBalancer` ，MetalLB 就会自动分配 IP 吗？

A：只要你在 Service 中指定：
```

spec:  
  type: LoadBalancer
```

MetalLB 就会自动检测到这个 Service，并从你定义的 IPAddressPool（或 AddressPool） 中分配一个外部 IP 地址。

🧩 背后的原理（建议理解）

在 Kubernetes 中，当你创建一个 `type: LoadBalancer` 的 Service 时，本质上会发生一件事：

> 集群发出一个“我需要一个外部 IP”的请求

在云环境（比如 AWS / GCP / Azure）中：

  * • 这个请求会被云控制器接管
  * • 云厂商帮你创建一个真正的负载均衡器，并分配公网 IP

而在裸机环境中：

> 这个角色，就由 MetalLB 来承担

MetalLB 的工作流程是这样的：

  1. 1\. **controller 监听所有 Service**
  2. 2\. 发现有新的 `type: LoadBalancer` Service
  3. 3\. 从 `IPAddressPool` 中选择一个未使用的 IP
  4. 4\. 写入 `.status.loadBalancer.ingress`
  5. 5\. speaker 在节点上进行 ARP/NDP 广播
  6. 6\. 外部网络就可以访问这个 IP

你可以简单理解为：

> MetalLB = 自己实现了一套“云厂商 LB 控制器”

## 总结

通过本文的实践，我们在 Kubernetes 裸机环境中成功引入了 MetalLB，为集群补齐了 `LoadBalancer` 能力，也就意味着我们拥有了一个**高可用、标准化的 Service 对外入口** 。

这一步非常关键，它带来的不仅仅是“可以访问服务”这么简单，而是：

  * • 应用可以像在云环境中一样，通过 `LoadBalancer` 统一对外暴露
  * • 外部访问路径更加清晰、稳定，不再依赖 NodePort 等方式
  * • 为后续部署各类中间件和业务系统打下基础

有了这样一个稳定的入口之后，我们就可以更从容地在集群中部署更多应用，同时也能更方便地从集群外部进行访问和管理。
