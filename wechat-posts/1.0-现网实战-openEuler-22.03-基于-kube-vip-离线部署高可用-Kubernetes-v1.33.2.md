## 前言

这套环境的目标很明确：**一次部署成功，直接可用于生产环境** 。

我的需求并不复杂，但约束很现实：

  * • 必须 **离线部署** （内网环境）
  * • 必须 **高可用** （不能单点）
  * • 没有太多时间反复调整，希望 **一步到位**

基于这些前提，这套方案的核心思路是：

👉 尽量减少组件复杂度，同时保证稳定性和可维护性

## 高可用方案选型

在高可用实现上，我没有沿用传统方案：

> nginx + haproxy + keepalived

而是直接选择了一个更“现代”的方案：

👉 kube-vip

这么做的原因很简单：

  * • 部署更轻量
  * • 架构更清晰
  * • 与 kubeadm 集成更自然
  * • 少一层负载均衡组件，少一层故障点

对于现网环境来说，这种“减法设计”反而更可靠。

## 服务器规划

关于服务器的选型：  
开始选服务器的时候，我并没有要求服务器的配置具体如何，k8s 对于服务器配置也并没有严格的要求，在我们现网环境的闲置服务器中，能供选择的服务器并不多。

这两个类型的服务器的存储恰恰很满足我的要求，有足够的 SSD 和 HDD。

美中不足的是，worker 的内存比较小，master 节点的内存太大，导致后期有些组件部署的时候只有设置容忍，将部分组件调度到 master 节点运行。

#### 生成 containerd 配置

这里不考虑使用 harbor，即使我们现网有一个，走网络策略很麻烦，服务器有限的情况下，就直接分发镜像文件加载吧

```

```

所以 `config.toml` 这个配置文件的 `pause` 镜像没有调整

修改 `config.toml` , 新增 `SystemdCgroup = true`
```

sed -i '/ShimCgroup/a \ SystemdCgroup = true' /etc/containerd/config.toml
```

`SystemdCgroup = true` 的用处

让 `containerd` 的 `runc` 使用 `systemd` 作为 `cgroup` 管理驱动。

为什么要这样做？

> 如果你的节点是 使用 `systemd` 作为 `init` 系统（CentOS 7+/Ubuntu 18.04+ 等），Kubernetes 的 `kubelet` 默认也用 `systemd` 管理 `cgroup`。
> 
>   
> 
> 
> 如果 `containerd` 用 `cgroupfs` 而 `kubelet` 用 `systemd` ，就会出现 `cgroup` 驱动不一致 的情况，可能导致 `kubelet` 报错：
> 
>   
> 
> 
> failed to run Kubelet: misconfiguration: kubelet cgroup driver: "systemd" is different from container runtime cgroup driver: "cgroupfs"
> 
>   
> 
> 
> 所以推荐设置成 `SystemdCgroup = true` 来统一。
