 _**01**_

**不靠while true，**

**LoopX 怎么让Agent长期干活**

  

LoopX 把一个很重要的原则写进了架构里，叫 Lifetime Goals。

  

也就是让目标拥有独立于某一次 Session 的生命周期。

  

Goal 可以跨越Session 、Agent，甚至多个项目阶段长期存在。

  

但这并不意味着把权限无限交给 Agent。

  

恰恰相反。

  

LoopX 要求长期目标拆成一个个**有边界、可验证的动作** 。

  

每一个 Agent Turn 仍然必须经过当前权限、范围、Quota、验证和 Writeback，才能真正被算作一次有效推进。

  

这其实解决了长期 Agent 很关键的一个矛盾。

  

我们既希望 Agent 能自己连续干活，又不希望一句“把这个项目做好”就变成无限授权。

  

LoopX 的办法，就是把**长期目标** 和**短期执行权** 拆开。

  

目标可以长期存在。

  
但每一个 Agent Turn，都只能在当前领取的 Todo 和明确边界内推进一段工作。

  

完成之后，它还要把结果和证据写回来，再决定有没有资格进入下一轮。

  

长期 Agent 很容易出现一种情况，哪怕这一轮并没有新的信息，下一轮依然被定时器唤醒，然后继续读取上下文、调用模型、消耗 Token。

  

LoopX 因此专门维护 Compute Quota。

  

每次自动执行之前，Runtime 可以先询问：

```

loopx quota should-run
```

`  
`

看看这一次到底应不应该继续。

  

一轮任务真正完成并经过验证，再通过：

```

loopx quota spend-slot 
```

`  
`

为这次 Turn 记账。

  

如果任务现在应该等待用户、等待外部信息，或者已经没有值得推进的动作。

  

LoopX 可以让这一轮直接跳过，不再调用 Agent、也不消耗 Quota，并根据当前 Runtime 返回等待、退避甚至停止 Loop 的调度建议。

  

这也是 LoopX 和“给 Claude Code 套一个 while true”的区别。

  

**Loop 解决的是重复执行，LoopX 想解决的是这个 Loop 为什么继续、什么时候继续、谁继续，以及什么时候必须停。**

另外一个很有意思的设计，是 LoopX 并不要求所有任务都交给同一个 Agent。

  

它采用的是 **Peer Agent** 思路。

  

注册进系统的 Agent 默认是平级的，并不存在一个永久拥有最高控制权的“Manager Agent”。

  
谁来执行下一段任务，由 Todo Claim、Lease、Goal/Write Boundary、Continuation Policy、任务级分配以及相应的 Capability 准入条件共同决定。

  

比如一个功能开发任务，可以先由 Claude Code 领取 Implementation Todo。

  

Claude Code 写完代码并提交验证结果之后，Codex 再领取 Review Todo。

  

LoopX 自己不写代码，也不做 Review。

  

它更像站在这些 Agent 背后的控制面：记录谁正在做什么、上一阶段交付了什么证据、Review 有没有通过、现在卡在哪里，同时决定下一轮是否具备继续执行的边界、权限和计算预算。

  

 _**02**_

**安装教程  

环境要求：Python 3.11+、`curl`、`tar`，以及 macOS 或 Linux shell。

```

curl -fsSL https://huangruiteng.github.io/loopx/install.sh | bash
export PATH="$HOME/.local/bin:$PATH"
loopx doctor
```

  

然后在项目中连接loopx ：

```

cd /path/to/your-project
loopx connect
loopx status
```

  

如果项目尚未初始化，且 connect 明确提示缺少状态，可以走 guided path：

```

loopx start-goal --guided --project . --goal-text "你的长程目标"
```

  

可以让 agent 在当前项目里连接 LoopX、运行 loopx doctor、保留已有状态，并汇报当前 gate 和下一条 todo；然后用 $loopx <复杂任务> 或 /skills 里的 loopx。

 _**03**_

**总结  

LoopX 不试图取代任何 Agent Runtime，它只是在 Agent 和外部世界之间加了一层薄薄的控制面，把"状态"这件事从 Agent 的上下文里剥离出来，变成可查询、可恢复、可审计的东西。

  

如果 Agent 跑偏或者崩溃了，使用 LoopX 后就还能回到同一个目标上，知道前面发生了什么，知道下一步该从哪里接上。

  

对于已经在跑长任务的人来说，这挺实用。
