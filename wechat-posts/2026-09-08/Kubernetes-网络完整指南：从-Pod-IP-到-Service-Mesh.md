# Kubernetes 网络完整指南：从 Pod IP 到 Service Mesh

![cover](https://r2.jeanjan.kdns.fr/pictures/img-3299cdbc01.jpeg)

![](https://r2.jeanjan.kdns.fr/pictures/img-3299cdbc02.png)

如果你一直觉得 Kubernetes 网络是一堆互不相干的概念，这篇文章会把它们串成一个可以真正装进脑子里的完整故事。

我们会自底向上搭建这套网络体系，不需要任何前置网络知识；遇到关键术语时，我会用通俗语言现场解释。有些地方会简化或省略，不会覆盖每个边界场景，但对建立整体理解来说，这些都不重要。

**事实上，我甚至不会放代码片段和图片，尽量让内容最简单，让你专注理解概念本身，而不是被代码干扰。**

那就从最底层开始吧。

## 1\. 每个 Pod 都有自己的 IP

在 Kubernetes 中，**每个 Pod 都有自己的 IP 地址** 。这解决了一个历史问题：以前应用直接部署在服务器上时，两个应用不能监听同一个端口，因为它们共享服务器的 IP。于是每个应用都得改端口，还得记着谁用了哪个端口。

Kubernetes 给每个 Pod 独立 IP，两个 Pod 就可以用同一个端口号监听，问题迎刃而解。

问题解决了，我们是不是就能通过 Pod 的 IP 和端口访问它了？技术上可以，但 Pod 不持久，所以这并不是最方便的访问方式。

于是有了下一层：**Kubernetes Service** 。

## 2\. Service

Pod 会重启、会被重新调度，每次都会拿到新 IP。你不能把一个可靠系统建立在不断变化的东西之上。

**Service** 解决的就是这个问题。它提供一个在 Service 整个生命周期内不变的稳定 IP。你访问 **Service IP** ，Service 会把流量转发给当前位于它后面的 Pod。Pod 来来去去，前面的地址始终不变。

Service 怎么知道后面有哪些 Pod？在 Service 定义里，你可以写一个 **selector** ，按标签匹配 Pod。例如，你的 Service 匹配所有带 `app: payment-service` 标签的 Pod。你需要给 Pod 打上对应标签，Kubernetes 会维护一个实时列表（这个列表叫 EndpointSlice），自动更新匹配标签的 Pod，并把 Service 的流量转发给它们。

所有 Service 都用同样的机制匹配 Pod，但根据流量需要到达的范围，Service 分成几种类型：

  * **ClusterIP** ：默认类型。给 Service 一个集群内才能访问的稳定内部 IP，用于服务之间的内部通信（例如后端访问数据库）。大多数 Service 都是这种类型。
  * **LoadBalancer** ：在 Service 前面创建真实的云负载均衡器（AWS、Azure、GCP 上都有），给你一个干净的外部 IP，是公开暴露服务的常规方式。缺点是每个 LoadBalancer Service 都会独占一个云负载均衡器，每个都要花钱。
  * **NodePort** ：在每个节点上开放一个固定端口，你可以通过任意节点的 IP 加这个端口从集群外部访问 Service。能用，但很笨拙：直接暴露了节点，还要管理端口号。主要用于快速测试，不适合生产。
  * **ExternalName** ：比较特殊，它不路由到任何 Pod，只是把 Service 名映射到一个外部 DNS 名称。当你希望用内部名称访问集群外的东西时很有用。

简单说，你平时主要会用到这两种：

  * **ClusterIP** 做内部通信，
  * **LoadBalancer** 把服务暴露到公网。

到这里都挺好的，不需要别的了吧？

再看看 LoadBalancer 的缺点：每个 Service 一个云负载均衡器，很快就不便宜了。如果有十个服务要暴露，就是十个负载均衡器、十张账单。所以把多个服务暴露到外部世界有更好的方式，也就是下一层：**Ingress** 。

## 3\. Ingress

上一节最后我们谈到了成本：每个 Service 一个云负载均衡器，很快就贵了。这是事实，但成本其实只是表象。更根本的问题是，LoadBalancer Service 是**笨的** 。

它只能把流量接进来转给一个 Service，仅此而已。它不能看请求内容，也不能决定请求该去哪。

这就是 **Ingress** 要解决的限制。Ingress 提供一个统一入口，主要按主机名和路径做路由。一个 Ingress 放在集群前面，可以把 `api.myapp.com` 转发给 API Service，把 `myapp.com/shop` 转发给商城 Service，全部通过**一个外部 IP** 、一个负载均衡器完成。

你定义路由规则，Ingress 把每个请求送到正确的 Service。这是普通 LoadBalancer 做不到的，因为它对请求内部一无所知。

所以 Ingress 解决的是真正的问题：不只是“负载均衡器太多”，而是“我们需要一个能把流量路由到正确位置的智能入口”。

用 Ingress 还能免费得到一点：TLS（HTTPS）可以在一个地方为所有服务统一处理，不用在每个 Service 上单独配置。

不过有个坑……

Ingress 本身只是一组规则，它自己不干活。你需要一个 **Ingress controller** （最常用的是 nginx、Traefik、HAProxy 等）来**真正实现** 这些规则。

麻烦在这里：基础 Ingress 定义只覆盖简单的 host 和 path 路由。再往上的高级网络能力，比如重定向、重写、流量切分，都得通过 Ingress 定义里的 **annotations** 配置。为什么这有问题？因为 Kubernetes 根本不知道 annotations 是什么意思，它们就像代码里的注释，只有 Ingress Controller 能理解，而且每个 Controller 的 annotation 都不一样。换一个 Ingress Controller，就要重写配置。

这种混乱正是更新方案出现的原因，也就是下一节：**Gateway API** 。

## 4\. Gateway API

Gateway API 从根源上修复了 annotation 问题：把配置从 annotations 变成**真正的规范** ，也就是 Kubernetes 能理解、能校验的字段。你写一次，在任何支持 Gateway API 的 controller 上行为都一样。

Gateway API 还按角色拆分职责，这在多个团队共享一个集群时很重要。用 Ingress 时基本只有一个资源，大家都去改，没有清晰方式区分谁拥有什么。Gateway API 把它拆成三个：

  * **GatewayClass** ：定义使用哪个 controller，由平台团队配置。
  * **Gateway** ：真正的入口点，包含端口和 TLS，由集群运维人员管理。
  * **HTTPRoute** ：某个具体应用的路由规则，由应用开发者自己管理。

平台团队管基础设施，每个应用团队管自己的路由，互不踩脚。用 Ingress 很难干净地做到这种分离。

一句话总结：Gateway API 是 Ingress 的更现代替代品。干的是同样的活，把外部流量送到正确的服务，但路由逻辑写在规范里而不是 controller 专属的 annotation 里，职责归属也清晰拆分。很多人认为它是这个层面未来的方向。

到现在为止，我们一直用 IP 地址访问东西：Pod IP、Service IP、外部 IP。但没人想跟裸 IP 打交道。下一层：**DNS** 。

## 5\. DNS

前面全是 IP 地址。Pod 有 IP，Service 有 IP，外部入口也有 IP。但没人想在自己的应用里硬编码 `10.96.0.42`。我们想要的是名字，比如 `payment-service`、`database`、`api.myapp.com`。把名字变成 IP 地址就是 DNS 干的事，而 Kubernetes 内置了 DNS。

这一层分两面：集群内部的名字，和集群外部的名字。

**集群内部** ，有一个以 Pod 形式运行的 DNS 服务器，叫 CoreDNS。每当你创建一个 Service，CoreDNS 会自动给它一个名字。所以应用不用去追 Service 的 IP，直接访问 `payment-service`，CoreDNS 就会解析成对应的 ClusterIP。创建 Service 后，立刻就能用名字访问，服务之间就是这样在内部互相找到对方的。

**集群外部** 是另一个问题。把应用暴露到互联网时，你希望一个真实的公网域名 `myapp.com` 指向它。通常你得登录 DNS 服务商（Cloudflare、Route 53、Azure DNS），手动创建记录。地址一变，又得重来一遍。

有个工具叫 **ExternalDNS** 可以自动化这件事。它监控你的 Service 和 Ingress，发现某个需要公开，就自动去你的 DNS 服务商创建记录，地址变化时也会保持更新。

两个地方是同一个思路：有东西盯着正在运行的资源，让名字始终指向正确的 IP，你完全不用管 IP。CoreDNS 管集群内部，ExternalDNS 管集群外部。

现在我们可以用名字访问一切了，不错。

但有个小问题一直被我们忽略了，你能想到是什么吗？

到目前为止，任何东西都能跟任何东西通信。每个 Pod 都能访问其他所有 Pod，没有任何限制。这很方便，但不太安全。

控制谁可以和谁通信，就是下一层：**NetworkPolicy** 。

## 6\. NetworkPolicy

前面说过，默认情况下，Kubernetes 集群里每个 Pod 都能访问其他所有 Pod。对生产系统来说这是问题：一旦某个 Pod 被攻破，攻击者可以从这里触达所有其他资源。

**NetworkPolicy** 就是用来收紧这个的。你可以定义规则，规定哪些 Pod 可以跟哪些 Pod 通信，按 Pod 标签、Namespace、IP 段和端口来匹配。例如：“只有 backend 能访问数据库的 5432 端口，其他一律不行。”

关于 NetworkPolicy 有件事很反直觉，值得了解：策略不是靠**阻断** 流量工作的，而是靠**放行** 。

在你创建第一个针对某 Pod 的 NetworkPolicy 之前，它允许一切流量；但当你创建第一个 NetworkPolicy 并选中该 Pod 时，默认行为反转：不再是放行一切，而是**除显式放行的流量外，全部拒绝** 。

所以一个选中 Pod 但没有列出任何规则的策略，并不是什么都不做，它会把这个 Pod 彻底断网。记住这个“一旦被选中就默认拒绝”的行为。

常见做法是主动利用这一点：先在一个 Namespace 应用一条拒绝所有流量的策略，再按需放回你想要的特定流量。

最后一点：NetworkPolicy 管的是集群内部 Pod 之间的流量，也就是**东西向流量** 。来自外部的流量是另一回事，由边缘的 Ingress 和 Gateway API 层处理，前面已经讲过。不同的问题，不同的层。

流量现在受控了，只差最后一点：服务之间的流量没有加密，也没有验证。任何能在网络上看到它的人都能读到内容。

保护这一层的就是最后一块拼图：**mTLS** 。

## 7\. mTLS 与 Service Mesh

服务之间的流量没有加密，服务之间也不会真正验证对方的身份。只要有人进入网络，就能读到服务之间流动的数据，甚至可以伪装成其中一个服务。

解决办法是借用保护网站的那套东西：**TLS** 。你每次访问 HTTPS 网站都在用 TLS，它加密流量，并证明服务器确实如它自称（就是浏览器小锁头背后的证书）。但普通 TLS 只验证一边：服务器向客户端证明自己，客户端是匿名的。

在集群内部，这不够。当支付服务收到调用时，它要确认调用方确实是自己声称的那个服务，而不是碰巧连进来的任何人。于是我们用 **mTLS** ，也就是双向 TLS。它和 TLS 一样，区别在于**双方都要证明身份** 。调用方也要出示证书，接收方验证它。任何一方都不跟无法确认身份的对方通信。

这就是服务间“零信任”的基础：没有任何东西仅仅因为位于集群内部就被信任，每条连接每次都要证明自己。

难点在于证书太多了。每个服务都要有自己的证书，每个服务都要验证其他所有服务，而且都要定期轮换。在几十个服务之间手工做这件事不现实。

所以实践中由 **service mesh** 来接管。Service mesh（Istio、Linkerd，或者 Cilium mesh）和你的服务并排运行，自动处理所有证书工作：给每个服务签发唯一证书、持续轮换、验证每条连接。应用代码完全不用改，加密和验证在底层透明完成。

Service mesh 做的还不止 mTLS，它还会处理流量管理和可观测性，但 mTLS 是它存在的核心原因之一。代价是 mesh 本身就是一套真实的基础设施，通常对较大或安全敏感的集群值得，对小而简单的集群则有点过度。

这就是整个栈的顶部：流量被路由、命名、控制，现在又端到端加密和验证。

## 8\. 藏在最底下的东西：CNI

现在我们已经拼出了 Kubernetes 网络的完整图景。但有一个一直在后台、却从未解释的东西：**CNI** （Container Network Interface，容器网络接口）。为什么需要它？

**因为 Kubernetes 自己不做 Pod 网络。**

这会让很多人意外。“给 Pod 一个 IP 并连上网络”这么基础的事，竟然不是 Kubernetes 核心做的，它把这整个任务交给一个叫 CNI 的插件。Cilium、Calico、Flannel 都是 CNI。你在搭建集群时选一个，实际工作由它完成。

事实上，一个没有安装 CNI 的全新集群是无法工作的：节点会一直停在 `NotReady` 状态，直到你装上 CNI，因为在此之前没有任何东西能把 Pod 网络接通。

这篇文章主线里的一切，Service、DNS、策略，都建立在 CNI 之上，默认相信扁平网络是通的。而正是因为有 CNI，它确实是通的。

## 9\. 回顾：完整图景

让我们把整个体系重新拼起来，因为这篇文章的重点从来不是单个组件，而是它们如何相连。

我们讲的每一层，都是为了解决它下面那层留下的问题：

  * 每个 **Pod** 都有自己的 IP，但 Pod 是临时的，IP 不断变化。
  * 于是 **Service** 在它们前面放一个稳定 IP，但只能在集群内部工作。
  * 于是 **Ingress** （以及它的现代继任者 **Gateway API** ）提供一个智能入口把服务暴露到外部，但它的世界里还是 IP 地址。
  * 于是 **DNS** 在 IP 前面放上名字，集群内用 CoreDNS，公网域名用 ExternalDNS，但这样任何东西都能访问任何东西了。
  * 于是 **NetworkPolicy** 控制哪些 Pod 可以跟哪些 Pod 通信，但流量仍然没有加密和验证。
  * 于是通过 **service mesh** 实现的 **mTLS** 让服务互相证明身份，并加密它们之间的流量。

而在这一切最底下，**CNI** 首先给每个 Pod 分配了 IP，让整个栈依赖的扁平网络真实存在。

这就是整个架构的形状：每一层都信任下面那层提供的稳定东西，并把下面的混乱藏起来。Pod 来了又走，IP 变了又变，一切都在不断移动，而这一层层的组件，都是为了让某样可靠的东西站在不停变化的东西前面。

一旦你这样看，Kubernetes 网络就不再是一堆需要死记硬背的独立概念。它是一个设计，一个问题一个问题搭起来的。这就是全部，也是我希望你能装进脑子里的那幅图。
