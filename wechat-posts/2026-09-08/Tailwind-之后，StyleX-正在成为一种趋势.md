# Tailwind 之后，StyleX 正在成为一种趋势

**作者**: 木兆纸
**发布时间**: 2026-09-04 16:57
**原文链接**: https://mp.weixin.qq.com/s/sG_9TMA4F99UgzWgbKjWFw

---

> 过去几年，Tailwind 几乎成了前端样式界的默认选择。用原子类写样式，顺手又高效，新项目一上来基本就选它。但现在，一些团队开始做出改变：Polar 在设计系统 Orbit 里放弃了 Tailwind，Meta 的 Astryx 也直接建在 StyleX 上。越来越多人在问：为什么从 Tailwind 换到 StyleX？其实 Tailwind 没变差，变的是写代码的人。

## 写代码的人变了

现在 Polar 发布的大部分 UI 代码，都有 AI（大语言模型）参与。速度确实快，但一致性不佳。

AI 写 CSS 或 Tailwind 类很熟练，写得挺流畅，但它不懂背后的设计意图。让 AI 搭一张卡片，它会用 `p-4`、`rounded-lg`、`bg-gray-100`、`dark:bg-zinc-900`、`text-gray-500`。每个值单独看都没问题，但没有一个能保证来自你自己的设计系统。成百上千个组件、成千上万次生成后，界面会慢慢分化出千百种略有差异的灰色，哪怕你已经在提示文档里写满了约束。

Tailwind 的开放性，在主要由人写代码的项目里是实打实的好处。现在写代码的换成了 AI，同样的开放性就成了麻烦的源头 - 工具得跟着换，才能管住 AI。

## 类是字符串，字符串必然走样

Tailwind 类本质上就是字符串。`className="flex p-4 bg-blue-500"` 在到达编译器之前只是一段文本。写起来快是因为这个，让生成代码充满风险也是因为这个。

字符串给了 AI 无限的空间去犯小错：

  * • `p-4`、`p-5`、`p-[17px]`、`px-4 py-3`，全都合法，间距却各不相同
  * • `bg-gray-100`、`bg-zinc-100`、`bg-neutral-100`，全都合法，却没有一个是规范写法
  * • `dark:` 变体需要 AI 记得加，它有一半时间会忘
  * • `text-[#3b82f6]` 这种任意值，直接绕过你的调色板

这些都不是语法错误，都能通过检查，都能正常渲染。问题不在语法，在于静态分析抓不到的地方——它们脱离了设计系统。AI 无从知道你们系统里的灰色是 `oklch(0.96 0.003 264)` 而不是 `bg-gray-100`，因为类型系统里没有任何东西告诉它。

还有一个更深的问题，跟谁在打字无关。设计系统不是一堆数值，而是一组决策。卡片该用什么背景，弱化文字该用什么颜色，堆叠元素之间间距该多大 - 这些都是决策。`p-4` 只是个数值，不是决策；`bg-gray-100` 也只是个灰色数值，你不知道这个灰是用在卡片上、悬停态上、禁用控件上，还是纯属碰巧。用数值写代码，决策在写下的那一刻就丢了。半年后你有 40 处 `bg-gray-100`，想换卡片背景色，只能到处搜索颜色值，改不了任何决策。

## StyleX 把设计标记变成唯一词汇

因此迁移的方向很清楚：标记要按“用途”命名，而不是按“数值”。`background-card` 是一个决策，它在浅色或暗色下最终显示成什么色号，只是藏在这个名字背后的实现细节。间距也一样，`m`、`l`、`xl` 是间距等级里的角色，不是你碰巧喜欢的像素数。

StyleX 在这里扮演的是“机制”角色。它是 Meta 出品的编译期、类型安全的样式库。用 StyleX，你搭出来的只是一个接受带类型标记的 `<Box />` 组件，其他东西基本不收。Polar 这套 API 的思路来自 Shopify 的 Restyle 系统。

这是 Orbit 的写法：

●●●
```

<Box  
  flexDirection="column"  
  gap="l"  
  padding="m"  
  backgroundColor="background-card"  
  borderRadius="m"  
  borderColor="border-primary"  
  boxShadow="m"  
>  
  <Text variant="heading-xs" color="text-primary">  
    Card title  
  </Text>  
  <Text color="text-secondary">Description</Text>  
</Box>
```

每个值都来自一个决策。`padding` 不接受“16px”，只接受一组预定义的尺寸选项。`backgroundColor` 不接受色号，只接受真正定义过的颜色名称。类型直接来自标记定义：

●●●
```

export const spacing = stylex.defineVars({  
  none: '0',  
  xs: '4px',  
  s: '8px',  
  m: '12px',  
  l: '16px',  
  xl: '24px',  
  '2xl': '32px',  
  '3xl': '48px',  
  '4xl': '64px',  
  '5xl': '96px',  
})  
  
export const backgroundColors = stylex.defineVars({  
  'background-primary': 'light-dark(hsl(233, 4%, 81%), hsl(233, 4%, 3.5%))',  
  'background-card': 'light-dark(hsl(240, 2.90%, 72.50%), hsl(233, 4%, 9.5%))',  
  // ...  
})
```

设计决策集中存放在一个地方，而且也是组件属性类型唯一接受的东西。生成 Orbit 代码的 AI，不是在 CSS 的广阔空间里自由选择，而是在一份写好的短菜单里做选择。自动补全会向它展示合法的标记，拼写错误会变成类型报错，而不是三周后才被发现的视觉走样。

## 禁止裸 div

这套机制只有在你没法绕过它的时候才管用。裸 `<div>` 可以接受任何 className、任何内联样式、任何属性，它是一张空白画布，是绕过标记的那条路。如果旁边还有不受约束的 div 可用，那约束 Box 的属性就毫无意义。

所以 Orbit 不只是给属性加类型，还把无类型的容器整个拿掉。过去你会随手写 `<div>` 的地方，现在必须用 Box。旁边没有另一条平行的、不受约束的路，而且 Box 还恰好少打一个键。

语义上的顾虑也有解。Box 是多态的，`as` 属性可以把它渲染成 `nav`、`ul`、`li`，DOM 里依然是真正的语义元素，对应的 DOM 属性也会带着类型传递过去。丢掉的只是开放的字符串表面，不是语义。这条规则用 Oxlint 强制实施：

●●●
```

'polar/no-raw-html-layout': 'error',
```

让错误的东西编译失败，是目前唯一能在 AI 每次全新的上下文窗口里真正起作用的指令。写在文档里的规则只是“建议”，编码进 CI 的规则才是“契约”——PR 是绿的就可以放心合并，出了偏差没被规则抓到，那是规则有缺口，不是作者的错。

## Astryx 的另一半答案：给 AI 好例子抄

Meta 的 Astryx 把同一套逻辑又向前推了一步，它的出发点更朴素：AI 就是个模仿者。

Astryx 早期的模板质量不好，太多裸的 StyleX，太多 div 和 span，缺少真正的组件。让 AI 搭一个页面，它要么几乎不用 Astryx，要么交回一堆一看就是坏掉的代码。团队困惑了很久：AI 有文档、有每个属性的说明、有命令行里的每个例子，为什么全都不理？答案太简单了——它在抄坏例子。垃圾进，垃圾出。于是他们给模板写了一份评分清单，每次都按同一套标准打分，不允许任何一次马虎过关。把 AI 抄的东西修好，输出自然就跟着变好了。

接下来是可用性。一个整页的例子只在你的需求恰好跟它一模一样时才有用，而需求千差万别，靠整页模板覆盖所有情况不现实。所以例子做成三种尺寸：page 是完整页面模板，block 是更小的可组合区块，component 是单个组件的正确用法。从整页到最小组件，高质量示例铺满了整个范围。

再往上一步，是 `astryx build` 这个命令。它接收自然语言提示，返回跟你要做的事相关的模板。它不是丢回一长串结果，而是推荐第一步该做什么，让 AI 知道从哪开始。底层是个纯排序算法：一次性收集组件、钩子、文档、模板里的所有候选，清掉提示词里的废话，用一个内置同义词表把“dashboard”扩到“analytics”“KPIs”“metrics”，再做词干处理，“chart”和“charts”归到同一个词根。候选按固定阶梯打分：精确名字匹配最高，精确关键词其次，编辑距离近的再次，只出现在描述里的词排最后。整个过程没有网络调用，没有模型，是确定性的，同一个提示永远返回同一个结果。

每次 `astryx build` 结尾还会给一小段规则：不用 div 布局，不写内联样式，其余全用标记。就是那份评分清单，但这次对准的是 AI，而不是设计师。AI 仍然可以即兴发挥，围栏只是把它留在系统里。

两条线放到一起，迁移的完整逻辑就出来了。Polar 做的，是把设计决策变成类型系统里唯一能表达的东西；Astryx 做的，是把好的表达范例放到 AI 一定会去找的地方。一个收窄词汇，一个给好样例；一个防走样，一个给方向。

## 暗色模式不会忘

StyleX 还顺手解决了一个老麻烦。看标记的值：`light-dark(hsl(233, 4%, 81%), hsl(233, 4%, 3.5%))`。每种颜色同时带着浅色和暗色两个值，由浏览器原生的 light-dark() 函数解析。没有 `dark:` 变体要记，因为根本没有第二套样式。AI 无法发布一个浅色正常、暗色坏掉的组件，因为独立的暗色代码压根不存在。这类最常见的主题 bug，在 StyleX 里根本造不出来。

## 迁移才刚开始

现在下定论还早。Polar 应用的大部分还是遗留的 Tailwind，碰到哪个文件就迁哪个，没有搞一次大重写；封闭的标记集目前还覆盖不了所有要搭的 UI，所以每周都在加标记。Astryx 也还在早期。但方向是清楚的。

设计系统曾经是一组你希望人们遵守的决策。当大部分代码由 AI 编写的时候，“希望”就不再是策略了。设计系统必须变成一组决策，而且是唯一能表达出来的决策。这整场迁移，做的就是一件事：把“希望大家遵守”换成“只能这么写”。对于一个模仿者，给它值得抄的东西，它就开始有品位了。
