# 2026 年每个工程师都该知道的 9 种云架构模式

![cover](https://r2.jeanjan.kdns.fr/pictures/img-47672e0c01.jpeg)

> Netflix、Amazon、Uber、Spotify 和每个现代云原生应用背后的架构模式。

## 引言：学云服务容易，学架构才让你有价值

大多数工程师开始学云计算时，通常是在背服务名称。通过认证后觉得自己行了。然后第一个生产项目来了，资深工程师说的是"用微服务构建"、"这应该是事件驱动的"、"Serverless 更合适"。

注意到了吗？没人在讨论具体的 AWS 服务了。他们在讨论**架构模式** 。云服务只是积木，架构模式决定这些积木如何协同工作来解决业务问题。

同一个 AWS Lambda 服务可以是 Serverless 架构、事件驱动架构、管道架构或发布-订阅架构的一部分。服务不定义架构，**设计** 定义架构。

## 什么是架构模式？

架构模式是可复用的蓝图，已经成千上万次解决了常见工程问题。它们定义了服务之间的交互方式、数据流向、扩展策略和容错机制。

## 模式 1：Serverless 架构

Serverless 不是"没有服务器"，而是"你不用管服务器"。云提供商负责所有服务器管理：配置、扩展、补丁、维护。你只为实际执行时间付费。

**工作方式：** 事件触发函数执行，函数处理完后释放资源。没有请求时不产生费用。

**典型架构：**
```

用户请求 -> API Gateway -> Lambda 函数 -> DynamoDB  
                                |  
                                v  
                            SNS 通知 -> 另一个 Lambda  

```

**AWS 服务：** Lambda、API Gateway、DynamoDB、S3、SNS/SQS

**真实案例：** Coca-Cola 的自动售货机支付系统。每个售货机是一个 IoT 设备，用户扫码支付时触发 Lambda 处理交易。高峰期自动扩展，夜间零成本。

**优势：** 自动扩展、按需付费、快速开发、高可用

**局限：** 冷启动延迟、执行时间限制（15 分钟）、厂商锁定

## 模式 2：微服务架构

将大型单体应用拆分为小型、独立部署的服务，每个服务负责一个业务能力。

**工作方式：** 每个微服务有自己的数据库、独立部署、通过 API 或消息队列通信。
```

用户 -> API Gateway -> 用户服务 (独立 DB)  
                    -> 订单服务 (独立 DB)  
                    -> 支付服务 (独立 DB)  
                    -> 库存服务 (独立 DB)  

```

**真实案例：** Netflix 将单体 DVD 租赁系统拆分为 700+ 微服务。每个服务独立部署、独立扩展。推荐引擎和视频编码服务可以各自扩展，互不影响。

**优势：** 独立部署、技术栈自由、独立扩展、故障隔离

**挑战：** 分布式复杂性、数据一致性、服务发现、链路追踪

**最佳实践：** 每个服务一个数据库、API 版本化、断路器模式、服务网格（Istio/Linkerd）

## 模式 3：事件驱动架构

系统组件通过产生和消费事件来通信，而非直接调用。

**工作方式：** 事件生产者发出事件到事件总线/消息队列，事件消费者订阅感兴趣的事件。生产者和消费者完全解耦。
```

订单服务 -> 发布"订单创建"事件 -> EventBridge/SQS  
                                    |  
                    +---------------+---------------+  
                    |               |               |  
              库存服务          支付服务        通知服务  
              (扣库存)          (处理付款)      (发邮件)  

```

**真实案例：** Uber 的实时位置更新系统。乘客 App 持续发布位置事件，附近司机 App 消费这些事件显示在地图上，同时调度系统消费事件进行匹配。

**优势：** 松耦合、异步处理、自然扩展、事件回放

**挑战：** 事件顺序保证、幂等性、调试困难、最终一致性

## 模式 4：CQRS（命令查询职责分离）

将写入操作（Command）和读取操作（Query）分离到不同的模型和服务中。

**适用场景：** 读写比例严重不均的系统（如社交平台的 feed：大量读、少量写）
```

写请求 -> Command 服务 -> 写数据库 (优化写入)  
                            |  
                        事件同步  
                            |  
读请求 -> Query 服务 <- 读数据库 (优化查询，如 Elasticsearch)  

```

## 模式 5-9 概览

  5. **管道架构** \-- 数据流经一系列处理阶段，每个阶段做特定转换。适用于 ETL、日志处理。
  6. **发布-订阅（Pub/Sub）** \-- 发布者广播消息，订阅者按兴趣接收。适用于通知系统。
  7. **Sidecar 模式** \-- 辅助容器与主应用容器部署在同一 Pod，提供横切关注点（日志、监控、代理）。
  8. **Strangler Fig（绞杀者模式）** \-- 逐步替换单体应用：新功能用新服务实现，旧功能逐步迁移。
  9. **Saga 模式** \-- 分布式事务管理：将长事务拆分为一系列本地事务，每个有对应的补偿操作。

## 如何选择架构模式

| 需求        | 推荐模式          |
|-----------|---------------|
| 低流量、快速上线  | Serverless    |
| 复杂业务、团队拆分 | 微服务           |
| 异步处理、松耦合  | 事件驱动          |
| 读写分离、高读负载 | CQRS          |
| 数据处理管道    | 管道架构          |
| 渐进式单体迁移   | Strangler Fig |
| 分布式事务     | Saga          |

没有"最好的"架构模式，只有"最适合"的。真实系统通常是多种模式的组合：微服务架构中每个服务可能用 Serverless 部署，服务间用事件驱动通信，读写用 CQRS 分离。
