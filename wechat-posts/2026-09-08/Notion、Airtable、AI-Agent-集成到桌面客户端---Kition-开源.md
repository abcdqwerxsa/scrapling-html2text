Kition 是一个面向真实工作的 AI 桌面工作区：让文档、数据表、浏览器、Agent 与 Workflow 围绕同一份项目上下文协作，并让 AI 对文本的修改清晰可对比、可检查。

**桌面版下载：** github.com/KitionAI/kition/releases/latest

现在的 AI Agent 已经可以搜索网页、读取文件、调用工具、生成图片，甚至连续工作几十分钟。单看 Demo，它似乎已经离“自动完成工作”不远了。

与此同时，Agent 的能力越来越强，稳定用于日常工作的用户增长却相对缓慢。

很多 AI 产品提供的核心界面，仍然只是一个空白输入框。

用户需要自己告诉 Agent：资料在哪里、任务按什么顺序执行、每一步输出什么格式、结果保存到哪里。遇到偏差时，用户还要定位问题，再重新组织提示词。

熟悉模型、数据结构和自动化的开发者，可以把这种方式当作自由。更多用户只想完成工作，他们更需要清晰、熟悉的操作方式。

我们逐渐意识到：

> AI 已经拥有强大的“大脑”，还需要一张能够看见资料、结构和流程的工作台。

这就是我们做 Kition 的起点。

先用一句话概括我们的判断：

> **聊天框适合表达意图，但真实工作还需要持续的上下文、明确的数据结构、可检查的结果，以及能够重复执行的流程。**

Kition 希望给 Agent 提供一套可以长期工作的环境，让它从对话走进真实任务。

## **Agent 进入真实工作，还需要什么？**

真实工作通常从一个简短、模糊的需求开始。

以“帮我整理最近的业务数据并生成报告”为例，Agent 还需要了解这些信息：

  * • 数据在哪一张表里？
  * • 哪些列是收入、成本和回款？
  * • 报告应该使用什么结构？
  * • 原始数据变化后，报告如何更新？
  * • 最终结果应该保存在聊天记录、文件还是业务系统中？

人们使用传统软件时，可以直接从界面理解这些规则。表格的列名、字段类型、筛选条件和当前视图，本身就在表达上下文。

在以对话为主的 Agent 产品中，用户常常需要把界面和数据结构中的信息重新翻译成自然语言。

换句话说，用户往往要先描述需求、设计流程、检查质量，Agent 才能开始工作。

因此，很多 Agent Demo 看起来非常震撼，长期使用时却容易变成“问一句、复制一段、再粘贴到别处”。

## **让文档、表格和 Agent 共享上下文**

许多产品已经提供成熟的在线文档和在线表格。数据分布在不同云服务中，Agent 则来自另一个系统。

真正影响体验的是：服务边界会把上下文切开。

当 Agent 同时处理文档、表格、图片和附件时，需要适配不同的账号权限、API 能力、数据格式和同步状态。它有时只能看到一段复制的文字、一份临时上传的文件，或者经过裁剪的表格片段。

生成结果后，Agent 还需要把内容准确写回原来的文档位置或表格字段。

于是产生了新的上下文损耗：

> 数据已经存在，Agent 需要看到完整内容；任务已经完成，结果还需要进入工作系统。

当用户每次都要上传项目资料、解释表格，再手工搬运结果时，AI 就成了一个能力很强的“中间站”。共享上下文可以缩短这段路程。

## **桌面工作区，为 Agent 提供完整的工作环境**

Kition 把 Markdown 文档、结构化数据表、浏览器研究、AI Agent 和可视化 Workflow 放进同一个项目工作区。

这里的“桌面”既代表安装在电脑上，也代表一个明确、持续的工作边界：

  * • 文档提供完整的语义和背景；
  * • 表格提供字段、类型、记录和状态；
  * • 图片与附件提供原始材料；
  * • Agent 负责探索和判断；
  * • Workflow 负责重复执行已经确定的步骤；
  * • 模板提前封装提示词、字段关系和输出格式。

我们可以把 Agent 在真实工作中的有效能力粗略理解为：

Agent 的有效能力 = 模型能力× 上下文完整度× 可操作对象数量× 结果可持续性

当 Agent 主要通过聊天工作时，结果通常停留在聊天记录中。

当 Agent 能读取当前文档、理解表格字段、处理附件，并把结果写回工作区，一次生成就能变成可修改、可筛选、可复用、可自动执行的工作资产。

这也是 Kition 与纯聊天式 Agent 的核心区别：**对话负责启动任务，写回工作对象负责完成任务。**

## **AI 可以直接修改文档，但每一处变化都应该看得见**

让 AI 写回文档之后，一个新的问题随之出现：它究竟改了什么？

如果 AI 直接覆盖原文，用户往往只能重新通读整篇内容，才能判断哪些信息被增加、删除或改写。对于方案、报告、合同说明和对外文章等重要文本，这种不可见的修改会显著增加审核成本，也会削弱用户对 Agent 的信任。

![](https://r2.jeanjan.kdns.fr/pictures/img-9fb081f902.jpeg)

Kition 将**AI 修改与文本对比** 放进同一个文档工作流。用户可以让 Agent 根据要求直接修改当前文档，并通过文本对比查看修改前后的差异，再决定是否保留这些调整。

![](https://r2.jeanjan.kdns.fr/pictures/img-9fb081f903.jpeg)

这意味着 AI 不只是给出一段需要手工复制的建议，而是能够真正参与编辑，同时把修改过程交还给用户检查：

  * • 原文和 AI 修改结果可以直观对照；
  * • 新增、删除和改写的内容更容易定位；
  * • 用户不必重新通读全文来寻找变化；
  * • AI 可以大胆执行，最终决定权仍然留在用户手中。

> **可执行的 AI 很重要，可审查的 AI 同样重要。文本对比让“让 Agent 帮我改”从一次黑盒覆盖，变成一次透明、可控的协作。**

这项能力尤其适合文章润色、报告更新、需求文档迭代和多人协作审阅，也是 Kition 把 Agent 引入真实文档工作的关键亮点。

## **文档、表格、Agent 和 Workflow 分别解决什么问题？**

在 Kition 中，这四种能力对应工作从模糊到确定的不同阶段。

> 文档承载意义，表格承载状态，Agent 处理不确定性，Workflow 沉淀确定性。

文档适合记录背景、分析过程和最终报告；表格适合管理批次、字段、附件与状态；Agent 适合研究、识别和生成；当一套方法被验证有效后，再交给 Workflow 稳定重复。

用户可以从熟悉的动作开始：添加一条记录、上传一张图片、运行一个 AI 字段，或者打开一个已经配置好的模板。工具选择和复杂提示词可以交给系统与模板处理。

下面是 Kition 当前内置的几个真实场景。

## **场景一：一张表批量生成横版和竖版视频封面**

制作视频封面包含人物一致性、主题表达、构图和尺寸适配等多项要求。

同一批内容需要保持人物一致，同时根据主题、内容类型和情绪调整构图，还要适配 16:9 与 9:16 等不同发布平台。

Kition 的视频缩略图模板把这些要求拆成了明确字段：

  * • Key Message：视频要表达的核心信息；
  * • Face Photo：需要保持一致的人物参考；
  * • Content Type：教程、测评、生活方式等内容类型；
  * • Core Emotion：好奇、震惊、兴奋、神秘等情绪方向；
  * • Thumbnail 16:9 与 Thumbnail 9:16：对应不同渠道的生成结果。

![](https://r2.jeanjan.kdns.fr/pictures/img-9fb081f904.png)

每一行就是一个完整任务。用户可以一次管理多条内容，直接比较同一主题的多个版本，每张图片都对应明确的记录。

这里，表格同时承担了三个角色：输入界面、批处理队列和审核页面。

Agent 或图像模型负责生成，表格负责让生成过程变得可见、可检查、可继续。

## **场景二：识别票据图片，并自动变成结构化数据**

传统 OCR 通常只返回一段文字。

真实业务更关心结构化结果：把图片中的信息写入商户名称、地址、消费类别、结构化 JSON 和完整原文等字段。

Kition 的票据 OCR 模板允许用户把图片直接放进附件字段，视觉模型随后将识别结果写入同一行。

![](https://r2.jeanjan.kdns.fr/pictures/img-9fb081f905.jpeg)

截图中，每张票据都同时保留了：

  * • 原始图片；
  * • Vendor Name；
  * • Address；
  * • Category；
  * • Structured Data；
  * • Plain Text。

图片经过识别后，直接进入一张可以搜索、筛选、纠错和统计的数据表。

当票据数量增加后，用户还可以让 Agent 找出信息缺失的记录、汇总消费类别、分析费用变化，并将结论写成月度费用报告；经过确认的审核和通知步骤，则可以继续交给 Workflow。

## **场景三：从一个产品想法，扩展成完整设计资产**

产品设计通常包含多个相互关联的产物：概念图、正交视图、功能主图、使用场景、风格板和推广文案。

把每一项放在独立聊天中生成时，产品外形、参考图和版本容易分散。统一的数据表可以持续保留这些关联。

Kition 的批量产品设计模板把整条资产链放进同一张表中。文章开头的真实产品截图展示了这条流水线的完整界面。

用户从 Concept 和 Concept Description 开始，后续字段可以围绕同一条产品记录继续产生：

  1. 1\. Designs：多个产品设计候选；
  2. 2\. Orthographic Views：正视、侧视、后视和俯视等结构视图；
  3. 3\. Feature Image：展示核心功能的产品主图；
  4. 4\. Lifestyle Shot：真实使用场景；
  5. 5\. Style Board：材质、细节和场景组合；
  6. 6\. LinkedIn Copy 等发布文案。

关键在于：每个结果都与源记录、参考设计和前序产物保持关联。

修改产品描述后，用户可以快速找到需要重新检查的字段；对比方案时，也可以在同一张表中查看相关文件。

## **场景四：从业务表格生成一份可继续编辑的报告**

表格擅长保存数字，但管理者最终需要的通常是一份包含结论、风险和建议的报告。

我们在 Kition 中实际创建了一张 Business Metrics 表，记录 2026 Q1、Q2 和 Q3 Forecast 的收入、成本、毛利率、回款和应收款。

![](https://r2.jeanjan.kdns.fr/pictures/img-9fb081f906.jpeg)

随后让 Kition Agent 读取当前表格，比较不同时期的数据，并在工作区创建一篇中文 Markdown 报告。

Agent 调用了表格工具获取真实字段和记录，完成计算后，将《季度经营分析报告》保存回当前项目。

![](https://r2.jeanjan.kdns.fr/pictures/img-9fb081f907.jpeg)

报告会保存为一篇普通 Markdown 文档。用户可以继续修改、补充说明、建立内部链接，或者导出为 PDF 和 DOCX。

![](https://r2.jeanjan.kdns.fr/pictures/img-9fb081f908.jpeg)

这条链路说明了 Kition 希望建立的工作方式：

原始数据进入表格  
↓  
AI 字段识别、生成或分类  
↓  
用户在表格中检查结果  
↓  
Agent 跨记录分析  
↓  
结果写入可编辑文档  
↓  
Workflow 推动后续执行

## **为什么还需要 Workflow？**

Agent 适合处理目标模糊、路径未知、需要判断的任务。规则明确、需要稳定执行的任务，则适合交给 Workflow。

例如，每十五分钟同步一次邮箱、新记录产生后发送通知、金额超过阈值后进入审核，这些任务规则明确、需要稳定执行，更适合 Workflow。

![](https://r2.jeanjan.kdns.fr/pictures/img-9fb081f909.jpeg)

Kition 的 Workflow 使用可视化画布展示触发器和动作。用户可以查看每个步骤，补全缺失配置，单独测试节点，并检查运行历史。

因此，Agent 与 Workflow 形成接力：

> 把未知路径交给 Agent 探索，把已经验证的路径交给 Workflow 执行。

Agent 帮助找到方法，Workflow 负责重复执行已经验证的方法。

## **模板真正降低的，是“如何指挥 AI”的门槛**

很多人有明确的 AI 使用需求，也需要一套简单的方法，把真实任务拆成模型可以执行的步骤。

模板的价值，是把这部分经验提前固化：

  * • 哪些内容是输入字段；
  * • 哪些字段由 AI 生成；
  * • 输出应该是文本、图片还是结构化数据；
  * • 新结果依赖哪一个参考字段；
  * • 哪些步骤需要人工检查；
  * • 哪些操作可以进一步自动化。

用户面对的是一张已经表达任务结构的表，可以直接从填写字段开始。

降低 Agent 的使用门槛，就是把复杂能力放进用户熟悉的文档、表格、字段、按钮和模板中。

## **Kition 更关注“One Context”**

“All in One”经常意味着把更多功能入口放进同一个界面。

Kition 更希望实现“One Context”：不同能力围绕同一份项目上下文工作，共同使用同一批文件、数据和流程。

文档中的背景可以成为 Agent 的参考，表格中的记录可以成为操作对象，Agent 的结果可以写回文档和表格，成功的方法又可以转化为 Workflow。

最终留下来的是一组可以继续维护的文件、数据和流程。

桌面应用可以管理本地工作区。使用 Kition Cloud 或其他模型提供商时，提示词和用户选择的上下文会发送给相应服务。

重要的是，工作区中的文件、字段和操作对象是明确的，用户能够知道 AI 正在处理哪一份资料，以及结果被保存到了哪里。
