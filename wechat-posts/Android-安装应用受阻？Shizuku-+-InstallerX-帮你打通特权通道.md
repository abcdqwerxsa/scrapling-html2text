> Android 侧载限制收紧，这个 Shizuku 方案还能绕过

你试着从浏览器或者文件管理器里点开一个 APK，准备装个测试版或者修改后的应用，结果系统直接跳出不受信任来源的警告，甚至连安装按钮都点不下去。这种情况现在越来越频繁。Android 最近确实在收紧侧载的口子，很多用户发现原本顺手的流程突然多了阻碍。

![](https://r2.jeanjan.kdns.fr/pictures/img-104b68d501.png)

不过事情还没到完全堵死。有一个组合依然能用：Shizuku 配合 InstallerX Revived，把安装请求走 ADB 通道执行。**这个方法能绕过不少新加的限制，同时让操作流程保持相对顺畅。**

普通用户把侧载理解成“自己找应用装”，不像应用商店那样一键完成。开发者或者重度用户则靠它来试新功能、装国内商店没有的工具、或者用修改版提升体验。限制加强后，表面是安全考虑，实际却让一部分人觉得 Android 正在慢慢收紧原本开放的那部分空间。技术上看，新规大概针对普通未知来源安装意图做了额外校验，而 ADB 作为系统内置的调试通道，权限模型不同，所以绕过它的路径还存在。

Shizuku 就是那个中间角色。它先通过无线调试拿到系统级的执行能力，再把能力借给 InstallerX 使用。整个过程不需要 root，只靠手机自带的无线调试就能完成。配置多几步，但一次搞定后日常使用几乎无感。

## Shizuku 怎么把系统权限借给普通应用

把手机系统想象成一栋楼，普通应用只能在前台活动室活动，权限有限。ADB 是楼后的专用通道，权限高得多，但平时锁着。Shizuku 像个中间联络人，它先用无线调试的钥匙把后门打开一条缝，然后把临时通行证借给 InstallerX。InstallerX 拿到通行证后，就能完成普通安装器做不到的事。

没有这个中间层，用户要么忍受越来越麻烦的侧载确认，要么去刷 root。后者风险更高，操作也复杂。Shizuku 提供了一条中间路线，让高级功能继续可用，又不彻底打破系统的安全边界。实际使用中，它把安装请求转到 ADB 执行路径，而新限制似乎对这条路径的阻挡力度要弱一些。

Shizuku 在后台运行服务，通过无线调试或者 USB 调试和系统建立连接。配对成功后，它就能执行安装包之类的特权操作。授权给 InstallerX 之后，后者发出的请求就会走这条特权路径。thedjchi 维护的 fork 版本特别实用，因为它内置了 Watchdog。Android 系统为了省电经常杀死后台服务，这个 Watchdog 能检测到服务停止并自动拉起来，减少用户手动重启的次数。

我之前一直觉得这类权限桥接工具用起来很麻烦，得一直盯着后台状态。但实际配置好 Watchdog 和开机自启之后，它几乎是设好就忘的状态。具体是在试用这个 fork 版本时才发现，普通版本确实容易被系统干掉，而这个改进版把大部分维护工作省掉了。

顺便一提，配对用的六位数字代码每次都是动态生成的，这设计让临时连接的安全性更高一些。

## InstallerX Revived 让安装过程少了很多摩擦

普通安装器现在面对新限制会多出好几道确认，或者直接失败。InstallerX Revived 不自己去请求安装，而是把任务交给 Shizuku 处理。你点开 APK 文件后，流程更接近官方安装的顺畅感，少了很多中间阻挡。

对经常需要装测试版或者特定修改包的用户来说，这节省了时间和挫败感。系统层面，它利用 ADB 的信任机制，让安装请求在权限模型上更接近调试通道，而不是普通未知来源安装。结果就是部分新加的阻挡被绕过去了。

在 Shizuku 的授权列表里允许 InstallerX 后，这个应用就能调用 Shizuku 提供的接口来触发安装。整个过程数据走 ADB 相关通道，所以能避开部分针对普通包安装器的额外检查。它支持包括简体中文在内的多语言，界面也比较现代，稳定版和测试版都可以选。

配置完成后，打开任意 APK 文件，选择用 InstallerX Revived 打开，它就会接管后续步骤。安装请求就这样转到了特权通道。实际效果还是会受具体应用和系统版本影响，不是所有情况都百分百绕过。

## 从零开始设置整个流程

先安装 Shizuku。推荐直接用 thedjchi 维护的 fork 版本，因为它自带 Watchdog 自动重启功能。去对应 GitHub 页面下载最新安装包安装到手机。普通版本也能用，但服务容易被系统停止，你就得经常手动点启动。

接着开启开发者选项。打开设置里的关于手机页面，连点版本号七次，输入锁屏密码后就能看到开发者选项。进去之后，把 USB 调试和无线调试都打开。这两项是 Shizuku 建立连接的基础，没有它们，后续配对和启动服务都无法进行。

然后在 Shizuku 里启动服务。打开应用，选择通过无线调试启动，点击配对。系统会跳到开发者选项里的无线调试页面，点配对设备并输入配对码。保持那个配对屏幕别关，在 Shizuku 里输入显示的六位数字，确认开始。成功后你会看到服务运行中的提示。

如果用的是 thedjchi 的版本，这时候可以打开 Watchdog 开关和开机自启开关。这样即使手机重启或者系统偶尔清理后台，服务也能自己恢复，不用你反复操作。

最后装 InstallerX Revived。同样从 GitHub 下载安装。装好后回到 Shizuku 的授权应用列表，找到 InstallerX 给它权限。打开 InstallerX 本身，把安装方式改成 Shizuku 特权模式。

到这一步就完成了。以后遇到 APK 文件，直接用 InstallerX Revived 打开，它会自动走 ADB 通道安装，绕过不少新限制，体验也比默认安装器顺滑很多。配对时如果代码输错或者屏幕关了，就得重新来一次。授权那一步很关键，没授权的话 InstallerX 虽然能打开文件，但执行安装时会失败或者回退到普通模式。

这个流程对大多数从浏览器下载的 APK 都有效，其他从文件分享或者特定来源的情况处理方式类似，不展开说。

这个方案的核心在于把安装请求路由到 ADB 通道，利用系统对调试接口的信任来绕过部分新限制。设置虽然比直接点安装多几步，但一次配置后基本不用管，适合经常侧载的用户。

我原来觉得 Android 越来越封闭，这些 workaround 迟早会失效，但看到 2026 年还有活跃的工具在维护，就发现 ADB 这条路暂时还堵不住。具体到这个组合，它给了用户一个不需要 root 的实用选择。

如果你也经常需要安装非商店应用，不妨按照上面步骤试一次。配置过程中如果遇到配对失败，多检查一下无线调试是否真的开启了。
